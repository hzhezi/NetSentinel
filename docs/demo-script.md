# 演示脚本

> 答辩现场用。**照这个顺序做，不会漏步骤。**
> 全程约 5-8 分钟。

## 演示前 5 分钟准备

### 1. 起依赖服务

```bash
cd /Users/hazer/code/NetSentinel
docker compose up -d db redis
docker compose ps          # 确认两个 healthy
```

### 2. 起后端

```bash
./scripts/dev.sh
```

预期末尾出现 `Uvicorn running on http://0.0.0.0:8000`

### 3. 起前端（另开一个终端）

```bash
cd frontend && npm run dev
```

记下地址（通常是 `http://localhost:5173`，被占用时会换端口）

### 4. 确认 API Key 已配置

```bash
uv run python -c "from backend.core.config import settings; print('key 长度:', len(settings.DEEPSEEK_API_KEY))"
# 预期：key 长度: 35（不是 0）
```

> ⚠️ **若为 0**：AI 研判不可用，但检测与推送仍正常。
> 演示时直接说明"研判部分需 API Key，这里展示已有结果"。

### 5. 准备演示数据

```bash
# 演示数据已随仓库提供，确认存在：
ls data/logs/demo-eve.json data/raw/demo-traffic.pcap
```

**若不存在**，重新生成：

```bash
# 方式一：合成演示数据（最快，无需 Docker）
uv run python scripts/generate_demo_eve.py --count 40 --out data/logs/demo-eve.json

# 方式二：真实 pcap 过 Suricata（更能体现"真在检测"）
uv run python scripts/generate_demo_pcap.py
docker compose --profile suricata run --rm --entrypoint sh suricata \
  -c "mkdir -p /data/logs && suricata -r /data/raw/demo-traffic.pcap -l /data/logs"
cp data/logs/eve.json data/logs/demo-eve.json
```

### 6. 清空旧数据（可选，让演示从零开始）

```bash
docker compose exec -T db psql -U netsentinel -d netsentinel \
  -c "TRUNCATE alerts CASCADE; TRUNCATE triage_results CASCADE;"
```

## 演示流程

### 第 1 步：说明系统定位（30 秒）

> "这是一个**准实时 NIDS 检测与研判平台**。传统 IDS 只给一行告警；
> 本项目在检测之上加了 **LLM 研判层**——把原始告警变成带理由、
> 带处置建议、且**可审计**的结论。"

**打开浏览器首页（仪表盘）** → 当前是空的（刚清空过）。

### 第 2 步：启动数据重放（1 分钟）

**点击左侧「数据重放」**

1. 文件选 `data/logs/demo-eve.json`
2. **倍速填 `5`**（慢一点，能看清告警逐条出现）
3. 点「开始重放」

**立刻切到「实时告警」页**

> "注意看——告警是**一条条**冒出来的，不是一次全出。
> 系统按流量里记录的**事件原始时间戳**节奏重放，
> 复现了实时 IDS 的观感，但不需要真实网卡、不需要靶场。"

**观察点**：
- 时间列递增
- 严重度有不同颜色
- 大约 10-20 秒播完

### 第 3 步：演示 AI 研判（2 分钟）——**这是核心**

**在告警列表点任意一条签名的链接**进入详情页

**上半部分**：告警原始信息（五元组、分类、引擎）

**中间「L1 快速分诊」**：
> "L1 用轻量模型对**每条**告警做快速分诊。注意它的结论——
> 多数是「待人工复核」，置信度也偏低。
> **这不是模型不行，而是它拿到的信息确实不够**：
> 只有五元组和签名，无法判断这个 IP 是否恶意、目标资产多重要。"

**下方「L2 深度调查」→ 点右上角「深度调查」按钮**

> "现在触发 L2。它会**主动调用工具**收集证据：
> 查 IP 威胁情报、查关联历史告警、查目标资产重要性。"

**等约 10 秒**，然后：

> "看结论变了——从「待人工复核」变成「真实攻击」，
> 置信度从 45 升到 88。**证据补上后，模型才敢下判断。**"

**展开「调查过程（证据链）」**：
> "更重要的是这个——**每一步推理、每次工具调用、拿到什么结果，
> 都被完整记录**。结论可以逐行审计，而不是'AI 说啥就是啥'。
> 这在安全运营里是能落地的前提。"

### 第 4 步：展示评测数据（1 分钟）

**点击左侧「研判评测」**

> "这是用真实数据测出来的效果对比：
>
> L1 单独用：**一致率 0%**——9 条攻击告警全部判'待人工复核'
> L2 深度调查：**一致率 100%**——9 条全部正确判定，平均置信度 88，
> **零漏报**
>
> 成本上，L2 是 L1 的约 10 倍。所以架构上是
> **L1 全量筛、L2 选择性深入**，用'按需分配'控制成本。"

> "注意页面底部我标注了**评测局限**：样本量只有 9 条、
> 标准答案来自流量构造过程。这些限制必须说明，
> 不能把结果包装得比实际更强。"

### 第 5 步：展示日报与抑制规则（1 分钟）

**「安全日报」页**：
> "系统还能汇总生成安全日报，把统计数字写成可读的态势总结。
> 这里能看到 LLM 是否可用——不可用会降级为模板日报，
> **数字仍然准确，只是没有分析文字**。"

**「抑制规则」页**：
> "误报治理。比如内部扫描器每周固定扫描，
> 这类已知噪声可以配规则自动过滤，不占用分析师精力、也不浪费 LLM 费用。"

### 第 6 步：收尾（30 秒）

> "总结一下：
> **检测层**用 Suricata 规则引擎，10 种攻击类型实测全部命中；
> **研判层**是两级 LLM 架构，L1 筛、L2 深查，带可审计的证据链；
> **工程上**有 236 个后端测试、CI、容器化编排。
>
> 完整的设计文档与评测数据都在仓库里。"

## 常见问题应答

| 可能被问 | 怎么答 |
|---|---|
| **为什么不用机器学习？** | "实测过：留一验证下平均检出率仅 10.74%，无法弥补规则引擎'只能抓已知攻击'的短板。而随机切分下的 99.99% 是 CICIDS2017 已知的评估虚高。项目定位是'在现有 IDS 上加研判层'，不是另造检测器。" |
| **为什么要两层研判？** | "成本与质量的权衡。L1 便宜快但信息少，L2 贵慢但能调工具补证据。评测数据显示 L1 单独用一致率 0%，加 L2 后 100%。" |
| **LLM 会不会幻觉？** | "多重约束：强制结构化输出、MITRE 编号必须查表（不许凭记忆写）、查不到要显式说'未知'而非'安全'、`needs_human_review` 是一等结论。而且有证据链可审计。" |
| **为什么不用 Kafka/K8s？** | "单人项目，复杂度换不来收益。当前架构用 Redis + 单实例足够，且每一层职责清晰。" |
| **实时性如何？** | "演示用重放模式复现实时观感。架构上输入层已抽象——接网卡即可切换真实时，但本项目不做（明确列为非目标）。" |

## 演示失败预案

| 现象 | 处理 |
|---|---|
| 前端打不开 | 检查 `npm run dev` 是否还在；换端口访问 |
| 告警不出现 | 看后端终端日志；确认 eve.json 路径存在 |
| 研判一直是空 | API Key 未配 / 额度用尽 → 改为展示**已有评测数据**（评测页不依赖实时调用）|
| WebSocket 显示"连接中断" | 检查后端是否在跑；刷新页面 |
| 演示中系统崩了 | **切换到录屏**（建议提前录一份） |

> **建议**：正式答辩前**完整走一遍**，并**录屏备份**。
