## 二、核心论据：为什么需要两级研判

### 2.1 实测数据（可直接引用的表格）

| 指标 | L1 快速分诊 | L2 深度调查 |
|---|---|---|
| **结论一致率** | **0.0** | **1.0** |
| 给出明确判断 | 0 / 9 | **9 / 9** |
| 待人工复核比例 | **100%** | **0%** |
| 平均置信度 | 35 – 55 | **82 – 93** |
| 平均耗时 | ~2 秒 | 8,125 ms |
| Token 消耗 | 7,380 | 76,615 |

**评测配置**：样本 9 条（真实 pcap 产出）、L1 模型 `deepseek-chat`、L2 模型 `deepseek-reasoner`

### 2.2 结论表述（可直接抄进报告）

> 实验表明，L1 快速分诊在仅有告警基础字段（五元组、签名、分类）的条件下，
> 9 条攻击告警全部判定为"待人工复核"，未能给出任何明确结论。
> 引入 L2 深度调查后，通过调用威胁情报、关联告警、资产信息等工具补充证据，
> 9 条告警全部正确判定为真实攻击，平均置信度 88，零漏报。
>
> **该结果验证了两级研判架构的必要性**：单纯提升模型能力不足以改善研判质量，
> 关键在于为模型补充判断所需的上下文证据。同时，L2 的平均 token 消耗为 L1 的约 10 倍，
> 因此采用"L1 全量分诊、L2 选择性深入"的分级策略以平衡质量与成本。

### 2.3 复现命令

```bash
# 1. 生成含攻击特征的 pcap 并用 Suricata 处理
uv run python scripts/generate_demo_pcap.py
docker compose --profile suricata run --rm --entrypoint sh suricata \
  -c "mkdir -p /data/logs && suricata -r /data/raw/demo-traffic.pcap -l /data/logs"

# 2. 跑评测（真实 LLM 调用）
uv run python scripts/run_eval.py --with-l2
# 结果保存到 data/eval/eval_report.json
```

## 三、检测层验证数据

### 3.1 Suricata 规则命中情况

自建 11 条规则，覆盖 10 种攻击类型。用构造的 pcap（142 个数据包）验证：

| 攻击类型 | 命中数 | 严重度 |
|---|---|---|
| SSH 暴力破解 | 5 | medium |
| SQL 注入（UNION SELECT）| 1 | high |
| SQL 注入（OR 1=1）| 1 | high |
| 目录穿越 | 1 | high |
| XSS | 1 | critical |
| Log4Shell | 1 | critical |
| 反弹 shell | 1 | high |
| TCP 端口扫描 | 1 | medium |
| ICMP 扫描 | 1 | medium |
| DNS 隧道 | 1 | medium |
| **正常 HTTP 流量（4 条）** | **0（零误报）** | — |

**结论表述**：

> 检测层采用 Suricata 规则引擎，自建 11 条规则覆盖 10 种常见攻击类型。
> 用构造的测试流量验证：全部规则正常加载，10 种攻击类型全部命中，
> 同时 4 条正常 HTTP 流量未产生误报，验证了规则的准确性与低误报特性。

### 3.2 系统处理效果

```
Suricata 产出告警      11 条
    ↓ 去重（同源同签名聚合）
落库                    7 条
```

**去重效果**：SSH 暴力破解的 5 条相同告警被聚合成 1 条 —— 这正是防"告警风暴"的机制。

## 四、系统架构要点（报告"系统设计"章节）

### 4.1 分层

```
api/         路由层，零业务逻辑
services/    领域逻辑（归一化、去重、抑制）
repositories/ 数据访问
models/      ORM
detection/   解析器、重放 Feeder
agents/      LangGraph 图、工具集、三个 Agent
```

**依赖方向单向**：上层可依赖下层，下层不得反向依赖。

### 4.2 三个 Agent 的分工

| Agent | 触发 | 输入 | 输出 | 是否在主图 |
|---|---|---|---|---|
| Triage（L1）| 每条告警 | 告警基础字段 | 结构化分诊结论 | ✅ |
| Investigation（L2）| 条件升级 / 手动 | 告警 + 工具结果 | 结论 + 证据链 | ✅ |
| Report | 定时 / 手动 | 统计摘要 | 安全日报 | ❌ 独立任务 |

### 4.3 关键技术点（可作为"工程实践"亮点）

| 技术点 | 说明 |
|---|---|
| **准实时重放** | 按 eve.json 记录的**事件原始时间戳**节奏重放，复现实时 IDS 观感，无需网卡/root/靶场 |
| **统一告警模型** | 检测层输出归一化为 `UnifiedAlert`，下游不感知具体引擎 |
| **证据链** | L2 的每步推理与工具调用全部记录，结论可逐行审计 —— 不做黑盒 |
| **防幻觉设计** | 四重约束（见 §5）|
| **失败降级** | LLM 故障时告警不丢弃，降级为人工复核 |
| **误报治理** | 抑制规则（AND 逻辑 + 可选过期 + 空规则保护）|

## 五、防幻觉设计（答辩重点）

| 机制 | 实现 |
|---|---|
| **强制结构化输出** | API 层 `response_format=json_object` + 剥离代码围栏 + Pydantic 校验后重试 |
| **MITRE 编号必须查表** | 提供 `lookup_mitre_technique` 工具，prompt 明确"不得凭记忆输出编号" |
| **查不到说"未知"** | 工具返回显式标注"unknown 不等于安全" |
| **`needs_human_review` 是一等结论** | 给模型"承认不确定"的正当出口（仅允许二选一会迫使模型编造）|
| **严重度自主判断** | prompt 要求用自己的判断，不抄检测层上报值 |

**实测印证**：L1 对 9 条攻击告警全部给出 `needs_human_review` 且置信度 35-55 ——
**模型没有"表演确定性"，而是诚实指出了信息缺口**。这正是防幻觉设计生效的表现。

## 六、评估诚实性（必须写进报告）

### 6.1 已声明的局限

1. **样本量小**：评测仅 9 条，统计置信度有限，不能外推到大规模场景。
2. **标准答案来源有边界**：真值来自流量构造过程（攻击包 vs 正常包），
   真实网络中"攻击"与"正常"的边界更模糊。
3. **一致率口径**：仅在"模型给出明确判断"的样本上计算；
   `needs_human_review` 单独统计（它是审慎而非错误）。

### 6.2 历史认知保留（若被问及机器学习方案）

项目曾实现 CICIDS2017 + XGBoost 的 ML 检测，后**整体移除**。依据：

| 方案 | 指标 | 说明 |
|---|---|---|
| 随机切分 | F1 0.9999 | **已知的评估虚高**（流泄漏 + 特征泄漏）|
| 留一验证（模拟零日）| 平均检出率 **10.74%** | DDoS 21.45%、PortScan 0.03% |
| 特征重要性 | 包长类特征占 87.5% | 模型依赖的是流量指纹而非行为模式 |

**结论**：ML 无法真正弥补规则引擎"只能抓已知攻击"的短板，
且引入特征管道、模型版本管理等额外复杂度，与收益不成比例。
项目定位是"在现有 IDS 之上加研判层"，不是另造检测器。

## 八、答辩常见问题速查

| 问题 | 一句话回答 |
|---|---|
| 为什么不自己训练模型？ | 实测零日检出率仅 10.74%，补不上规则引擎的短板；定位是"IDS + 研判层" |
| 为什么两层研判？ | 成本质量权衡：L1 便宜筛全量，L2 补证据深查少数；实测一致率 0% → 100% |
| LLM 会不会幻觉？ | 四重约束 + 证据链可审计；实测模型会诚实说"信息不足" |
| 是否实时？ | 演示用重放复现观感；输入层已抽象，接网卡即可切实时（明确列为非目标）|
| 为什么不用 Kafka/K8s？ | 单人项目，复杂度换不来收益 |
| 有什么创新点？ | ①网络层检测→LLM 研判的链路集成（开源生态空白）②可审计的证据链机制 ③两级研判的成本质量平衡 |
